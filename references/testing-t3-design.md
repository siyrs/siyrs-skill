# T3 深度业务测试设计

本文件定义 **T3 测试资产如何设计与沉淀**。它服务于 `siyk-test-add` 在判断需要 T3 深度时，以及显式的 `siyk-test-add-t3`。

T3 的目标不是机械增加测试数量，而是理解真实业务后，设计能够证明关键业务关系、影响传播和影响隔离的高价值测试。

开始前同时遵循 [Siyrs Skill 第一性原则](principles.md)、[测试指南](testing.md) 和 [测试分级执行合同](testing-tiers.md)。

## 核心定义

> **全局理解，但不自动全局测试。**

T3 有两个不同范围：

- **认知范围**：为了理解业务，可以从项目全局建立必要上下文。
- **测试 Scope**：真正设计和沉淀 Case 的范围。

测试 Scope 默认来自当前用户目标、当前修改、受影响模块和必要 blast radius；用户明确指定模块、业务域、功能或全项目时，以用户范围为准。

不要因为需要全局理解，就把每次 T3 都扩大成全项目测试。

## 先建立业务模型，再设计 Case

优先通过已有信息快速建立业务认知：

```text
.siyrs/README.md（存在时）
→ 项目 README / docs
→ docs/testing/
→ 模块、页面、API、Domain / Service 结构
→ 当前 Scope 相关代码与测试
```

目标不是逐文件扫描整个仓库，而是确认真实存在的：

- Actors / 角色与参与者；
- Business Objects / 核心业务对象；
- Main Paths / 主要业务旅程；
- State Transitions / 状态流转；
- Permissions / 权限边界；
- Data Visibility / 数据可见范围；
- Relations / 上下游和跨模块关系；
- Side Effects / 通知、统计、缓存、审计、后台任务等真实副作用；
- Integration Boundaries / 外部系统或模块边界。

没有项目证据的能力不要因为模板里出现过就编造。

## 从业务事件设计，而不是从按钮设计

T3 Case 应优先围绕真实业务事件：

```text
Actor
对 Business Object
执行 meaningful Action
```

然后同时验证：

1. 操作者自身应发生什么；
2. 业务对象应发生什么；
3. 相关角色和相关数据应发生什么；
4. 相关页面、统计、权限和副作用是否保持一致；
5. **无关角色、无关数据和无关模块不应该发生什么。**

不要把“点击按钮后提示成功”当成完整 T3 验收。

## Impact Propagation 与 Impact Isolation

每个重要业务操作都同时思考两个方向：

### Impact Propagation — 影响传播

应该发生的影响必须正确传播，例如：

- 新状态是否传播到列表、详情、搜索、统计和关联页面；
- 新负责人或新成员是否获得正确权限和数据；
- 上下游对象是否产生真实定义的联动；
- 刷新、重新登录或重新查询后结果是否仍一致。

### Impact Isolation — 影响隔离

不应该受到影响的对象必须保持不变，例如：

- 无关角色不能获得新的可见性或权限；
- 无关项目、租户、组织或业务对象的数据不得被污染；
- 无关统计、状态、消息或关联记录不得变化；
- 一次业务操作不能破坏其他用户原有的合法状态。

**任何重要业务操作，都同时验证“应该改变什么”和“不应该改变什么”。**

## 多角色与连续业务旅程

存在多个真实角色时，优先设计跨角色连续旅程，而不是把每个页面拆成孤立操作：

```text
角色 A 创建 / 提交
→ 角色 B 查看 / 审批 / 处理
→ 角色 A 再次确认结果
→ 角色 C 验证自己的相关权限或无关隔离
```

根据真实项目选择角色，不要求每个 Case 都机械覆盖所有角色。

## 设计时重点思考的风险维度

以下是思考提示，不是 Case schema，也不要求每条用例都逐项填写：

- 角色与权限；
- 状态流转与非法状态；
- 数据可见性与数据隔离；
- 多角色协作；
- 影响传播与影响隔离；
- 列表 / 详情 / Dashboard / 搜索 / 统计等多视图一致性；
- 真实副作用；
- 失败、重试、撤回、回滚或恢复；
- 跨模块 / 外部集成边界；
- 并发、重复提交、幂等等真实存在的风险。

只纳入当前 Scope 和项目证据真正支持的维度。

## 复杂 Scope 的多视角分析

执行环境支持子代理且 Scope 足够复杂时，优先使用多个独立视角并行建立认知，例如：

- **Business Explorer**：业务对象、主路径、上下游、状态；
- **Role & Permission Explorer**：角色、权限、数据可见范围；
- **Impact Explorer**：影响传播、副作用、跨模块联动；
- **Isolation Explorer**：无关角色、无关数据和隔离边界；
- **Test Critic**：检查遗漏、弱断言、重复 Case 和无证据推断。

子代理是推理策略，不是运行依赖。环境不支持时，由主 Agent 按相同视角分轮完成。

不要把子代理原始输出持久化成 state、matrix、JSON registry 或 agent-results 文件；只把最终有长期价值的测试知识沉淀为 Markdown。

## Critic：沉淀前做一次批判复核

最终 Case 落盘前检查：

- 是否只测成功路径；
- 是否遗漏角色、权限和数据范围；
- 是否只测“应该变”，遗漏“不应该变”；
- 是否只看 UI 提示，缺少真实业务结果；
- 是否遗漏跨页面 / 跨模块一致性；
- 是否存在重复或近似 Case；
- 是否出现没有真实项目证据的业务想象；
- 断言是否足够证明业务结果，而不是只证明操作被接受。

## Markdown-first 沉淀

T3 的第一产物是高质量长期 Case，而不是自动化代码数量。

优先写入：

```text
docs/testing/cases/<module>.md
```

跨模块完整业务旅程可进入 `cross-module.md` 或项目已有同类文件。

推荐保持少量元数据 + 自然语言：

```markdown
### TC-PROJECT-021 负责人变更后的角色与数据影响

**P0 · UAT**

负责人 A 将项目负责人变更为 B。

验证：

- B 获得负责人应有的权限和数据；
- A 按业务规则失去仅属于负责人的能力；
- 其他项目成员原有权限保持不变；
- 无关用户仍然不能看到该项目；
- 相关列表、详情与统计正确变化；
- 无关项目的数据和统计不得变化；
- 刷新或重新登录后状态保持一致。
```

`T3` 是设计深度，不要求为了标记而给每条 Case 增加 `T3` 字段。`T2` 仍只用于固定 Smoke 成员；Unit / Integration / E2E / UAT 仍表示测试层。

## Case 与自动化

T3 Case 可以是：

- Case + 新增自动化；
- Case + 已有自动化真实路径；
- Case + Manual / UAT。

先判断场景是否值得和适合自动化，再决定是否新增 executable test。不要为了“全部自动化”把真实 UAT 扭曲成脆弱脚本。

新增自动化时继续放在项目原生测试目录，并运行新增测试和最窄必要验证。没有真实环境、账号、设备或数据时，如实记录 Manual / UAT 前置条件，不伪造测试通过。

## 最终边界

T3 测试设计默认可以新增或更新 Markdown Case，并在有价值时新增测试代码；默认不修改业务代码、不 commit、不 push、不 release、不 deploy。

不要为 T3 设计新增 command router、state、schema、matrix runtime、evidence registry、agent registry 或其他机器治理层。Markdown 和真实项目证据足够时，就保持 Markdown-first。
