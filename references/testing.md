# 测试指南

选择能够为本次行为变化提供可信证据的最低测试层级。只有当修改跨越真实边界、聚焦检查出现异常失败，或者用户明确要求更广泛验证时，才扩大测试范围。

## T1 — 聚焦验证

大多数普通修改从 T1 开始。

典型证据：

- 针对性的单元测试或组件测试；
- 与修改文件相关的类型检查、编译、lint、格式检查或静态分析；
- 针对被修改模块的窄范围回归 selector；
- 对纯文档或纯配置修改执行 parser / config 校验。

T1 应回答：**被修改的单元以及它的直接契约是否仍然正确？**

## T2 — 集成验证

当修改跨越有意义的系统边界，或者 T1 无法证明用户要求的真实行为时，使用 T2。

典型证据：

- API + 持久化，或消息 / job 行为；
- 前端 + 后端集成；
- 浏览器 smoke 或可访问性检查；
- Android 模拟器 / 真机流程、instrumentation、权限、生命周期或升级行为；
- 认证 / 授权边界；
- migration、容器、服务或基础设施集成。

T2 应回答：**受影响路径跨越真实集成边界后是否仍然正常工作？**

## T3 — 全量 / 验收

当用户明确要求全量测试、发布前验收、release gate，或者大范围高风险修改适合做完整相关回归时，使用 T3。

T3 应包含仓库定义的完整相关测试集，以及项目要求的 UAT / 发布检查。如果仓库没有正式的 release suite，应如实说明本次实际执行范围，不要虚构“完整覆盖”。

只执行 UAT 只能证明验收场景通过，不能自动代表所有 T3 回归层都已通过。

## 如何选择检查

| 修改类型 | 起步检查 | 何时扩大 |
|---|---|---|
| 文档 / 配置 | parse / lint / 定向校验 | 行为或部署语义发生变化 |
| 纯逻辑 | 聚焦单元测试 | 共享契约或数据结构变化 |
| 服务 / API | 单元 + 定向集成 | 持久化、权限、消息、job 变化 |
| 前端 | 组件 / 类型 / build | 用户流程、路由、API 或浏览器行为变化 |
| Android | 单元 / build | 真机 UI、生命周期、权限、owner/kiosk、安装/升级变化 |
| 数据库 / migration | migration 校验 | 影响既有数据或多个服务 |
| CI / build / deploy 配置 | 语法 / 配置检查 | 发布路径或运行时镜像变化 |

优先使用目标仓库已有 selector 和命令。现有测试框架能够表达所需检查时，不要再引入新的测试框架。

## 测试编写

以下情况应新增或更新测试：

- 可观察行为发生变化；
- Bug 修复需要一个回归用例；
- 未覆盖边界真实导致了问题，或可能掩盖同类问题；
- 用户明确要求新增测试。

不要添加只重复实现细节、没有验证价值的形式化测试。

## 验证证据

至少报告：

- 实际使用的命令或工具；
- 测试范围 / selector；
- pass / fail 结果；
- 会影响结果解释的重要环境信息；
- 被跳过或阻塞的检查及原因；
- 只有确实有用时才提供 artifact 路径，例如截图、视频、日志或覆盖率报告。

计划中的检查、根据代码推断的结果、以前缓存的执行结果，都不能冒充本次修改已经通过的验证，除非针对当前修改重新确认过。

## 测试工作区合同

测试相关工程工作必须有一个稳定、可发现的文档入口：`<project-root>/docs/testing/README.md`。

### 什么时候确保工作区存在

当当前任务需要新增测试、运行回归/集成/全量/UAT、维护测试约定，或者修改稳定验收契约时：

1. 先检查 `docs/testing/README.md` 是否存在；
2. 已存在时先读取它，再决定是否需要更新；
3. 不存在时，先检查真实项目结构、测试代码、构建文件和可执行命令，再创建该文件；
4. 不要为了满足形式而生成只有 TODO / 占位符的空文档。

纯粹不涉及测试或验收的工作，不要求为了“标准化”提前创建测试工作区。

### `docs/testing/README.md` 至少应说明什么

根据项目真实情况写有内容的部分，不要求为了模板完整度保留空章节。通常优先记录：

- 项目的测试入口和测试范围；
- T1 / T2 / T3 在该项目中的实际对应关系；
- 常用且真实可执行的测试命令 / selector；
- 必要环境、服务、设备、账号或测试数据前置条件；
- 长期有效的验收规则、发布检查或已知限制；
- 其他测试文档、模块说明或验收材料的链接。

它是测试知识的**统一索引和入口**，不是每次执行结果的流水账。

### 根 README 必须能发现测试入口

在 `<project-root>` 查找已有 README，文件名大小写不敏感，例如 `README.md`、`readme.md`、`Readme.md`。如果已经存在，更新现有文件，不要因为大小写不同再创建第二份 README。

优先把测试链接加到已有的“文档 / 开发 / 测试”导航区域；如果没有合适位置，可以追加一个很小的章节，例如：

```markdown
## 测试与验收

- [测试文档](docs/testing/README.md)
```

如果项目根完全没有 README，则创建标准 `README.md`，至少包含项目标题以及指向 `docs/testing/README.md` 的测试入口。项目标题优先使用仓库 / 目录已有名称，不要编造产品信息。

### 已有测试文档如何处理

如果仓库已经在 `tests/README.md`、`docs/qa.md`、模块目录或其他位置维护测试说明：

- 不强制搬迁；
- 不删除仍有效的文档；
- 创建或维护 `docs/testing/README.md` 作为统一索引，并链接到这些既有资料；
- 根 README 最终只需要稳定指向统一测试入口。

### 目录保持轻量

默认只保证：

```text
<project-root>/
├── README.md                  # 或已有的其他大小写形式
└── docs/
    └── testing/
        └── README.md          # 测试统一入口
```

只有当内容稳定、长期复用且主入口已经不适合承载时，才在 `docs/testing/` 下新增少量平铺文档，例如 `android.md`、`api.md`、`acceptance.md`。这些文件必须从 `docs/testing/README.md` 直接链接。

默认不要创建 `cases/`、`evidence/`、`matrix/`、run history、状态文件或深层目录。用户或项目已有约定明确要求时除外。

### 什么时候更新测试文档

以下变化应更新测试工作区：

- 测试入口、命令或 selector 发生稳定变化；
- 环境准备、设备要求、测试数据契约发生变化；
- 新增长期维护的模块测试说明；
- 稳定验收规则、release gate 或 UAT 规则变化；
- 根 README 中的测试索引缺失或失效。

普通重复执行、一次性的 pass / fail 结果、临时调试日志，不应默认写回测试文档。

## 证据与文档的边界

`docs/testing/README.md` 记录长期有效的测试知识；当前任务是否通过，仍必须依据本次实际执行的命令和结果。不要因为测试文档写着“通过”或记录了历史结果，就把它当成本次执行证据。
